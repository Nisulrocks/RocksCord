# Deploying RocksCord for free

The target is a single free web service that serves the API, the realtime gateway, and the
built client, backed by a free hosted database and free object storage.

**Total cost: $0. No credit card required at any step.**

Budget about 20 minutes.

---

## Why this combination

Real-time chat needs a *long-lived stateful process* for WebSockets, which is exactly what
serverless free tiers are bad at. That rules out Vercel and Netlify functions for the
server. The constraints that actually mattered:

| Requirement | Why it eliminates most options |
|---|---|
| Long-lived WebSocket connections | Serverless functions time out |
| No credit card | Fly.io, Railway, and most others require one |
| Free indefinitely, not a trial | Railway is a 30-day trial; Koyeb closed its free tier in 2026 |
| Persistent data | Free hosts rarely offer a persistent disk |

Render is the one mainstream host that clears all four. Its free tier does support
WebSockets (some blog posts claim otherwise — [Render's own docs](https://render.com/docs/free)
list WebSocket messages as traffic that keeps a service awake). Its lack of a persistent
disk is why the database is Turso and uploads go to Supabase.

## Step 1 — Database (Turso)

Turso is hosted libSQL, which is SQLite. Same dialect as local development, same
migrations, no schema changes.

Free tier: 5 GB, 500M row reads/month, 10M row writes/month, no card, no expiry.

1. Sign up at **[turso.tech](https://turso.tech)** (GitHub login).

2. Install the CLI:

   ```bash
   # Windows (PowerShell)
   irm https://get.tur.so/install.ps1 | iex

   # macOS / Linux
   curl -sSfL https://get.tur.so/install.sh | bash
   ```

3. Create the database:

   ```bash
   turso auth login
   turso db create rockscord
   ```

4. Collect the two values you will need:

   ```bash
   turso db show rockscord --url
   turso db tokens create rockscord
   ```

   Keep both — they become `DATABASE_URL` and `DATABASE_AUTH_TOKEN`.

You do **not** need to create tables. Migrations run automatically on first boot.

> Prefer the dashboard? You can create the database and a token entirely from the Turso
> web UI without installing anything.

## Step 2 — File storage (Supabase)

**Skip this if you do not need file uploads.** The blueprint ships with
`STORAGE_DRIVER=local`, so the service boots fine without any of this; uploaded files just
will not survive a restart. Come back and do this later if you want them to.

Free tier: 1 GB storage, 5 GB egress/month, no card.

1. Sign up at **[supabase.com](https://supabase.com)** and create a project.
2. **Storage → New bucket**, name it `rockscord-uploads`, and mark it **Public**.
   (Public is required: attachment URLs are unguessable capability links, which is the same
   model image CDNs use.)
3. **Project Settings → API**, copy:
   - the **Project URL** → `SUPABASE_URL`
   - the **`service_role`** key → `SUPABASE_SERVICE_KEY`

> The service-role key bypasses row-level security. It is used server-side only, after the
> request has already been authenticated and permission-checked. Never put it in a client.

## Step 3 — Deploy (Render)

1. Push this repository to GitHub.

2. Sign up at **[render.com](https://render.com)** with GitHub.

3. **New → Blueprint**, select the repository, and Render will read
   [`render.yaml`](../render.yaml). It declares the service, the build and start commands,
   the health check, and every environment variable.

4. Render prompts for the values marked `sync: false`:

   | Prompt | Value |
   |---|---|
   | `DATABASE_URL` | `libsql://rockscord-you.turso.io` |
   | `DATABASE_AUTH_TOKEN` | the Turso token |
   | `SUPABASE_URL` | your Supabase project URL, or blank |
   | `SUPABASE_SERVICE_KEY` | the `service_role` key, or blank |
   | `PUBLIC_URL` | leave blank for now |

   If you filled in the Supabase keys, also change `STORAGE_DRIVER` to `supabase` in
   **Environment**. It defaults to `local` so a first deploy cannot fail on missing keys.

   `JWT_SECRET` is generated by Render and stays stable across deploys, so shipping an
   update does not sign everyone out.

5. Click **Apply**. The first build takes 3–5 minutes.

6. Once it is live, copy the URL (e.g. `https://rockscord.onrender.com`) and set it as
   `PUBLIC_URL` in **Environment**, then redeploy. Attachment links are built from it.

   While you are there, tighten `CORS_ORIGIN` from `*` to that same URL.

### Not using the Blueprint

Create a **Web Service** manually with:

- **Build:** `npm ci && npm run build`
- **Start:** `npm start`
- **Health check:** `/health`
- Environment variables as in [`render.yaml`](../render.yaml)

## Step 4 — Verify

```bash
curl https://your-app.onrender.com/health
```

Expect `{"status":"ok","database":"up",...}`.

Then run the end-to-end check against it:

```bash
npm run smoke -- https://your-app.onrender.com
```

It needs the demo accounts. To seed a fresh production database once:

```bash
DATABASE_URL="libsql://..." DATABASE_AUTH_TOKEN="..." npm run db:seed -w @rockscord/server
```

Or just register an account through the UI and skip seeding entirely.

## Continuous deployment

Render redeploys on every push to `main` by default. From here:

```bash
git push
```

is the whole deployment process.

---

## Pointing the desktop app at your deployment

```
RocksCord.exe --server=https://your-app.onrender.com
```

The app then skips its embedded server and connects to the deployed one. The choice is
remembered in `%APPDATA%\RocksCord\config.json`.

## Free-tier limits to expect

| Limit | Effect | Mitigation |
|---|---|---|
| Render sleeps after 15 min idle | First request takes ~50 s | Warn your testers, or upgrade to $7/month |
| 750 instance-hours/month | ~31 days of one service | Fine for one service |
| Render has no persistent disk | Local uploads vanish on restart | Use Supabase Storage (step 2) |
| Turso: 500M reads / 10M writes per month | Far beyond a demo's needs | — |
| Supabase pauses after 7 days idle | Uploads 500 until unpaused | Open the dashboard to unpause |
| Supabase: 1 GB storage | ~125 files at the 8 MB cap | Delete old uploads |

**Keeping it awake:** a free [UptimeRobot](https://uptimerobot.com) monitor pinging
`/health` every 5 minutes prevents sleep — but it also burns your 750 hours in ~21 days.
Pick one: always-awake for three weeks, or on-demand all month.

## Alternatives

| Host | Free tier | Card | Notes |
|---|---|---|---|
| **Render** | 750 h/mo, sleeps at 15 min | No | The default here |
| **Northflank** | 2 always-on services + 1 database | No | **No sleep** — the best option if you want it always up |
| **Fly.io** | Small allowance | Yes | Needs `flyctl` and a Dockerfile (one is included) |
| **Koyeb** | Closed to new free users in 2026 | — | No longer viable |
| **Railway** | 30-day trial only | Yes | Not free long-term |
| **Oracle Cloud** | Genuinely generous, always free | Yes | A real VM; much more setup |

For Northflank: create a service from the repo, build `npm ci && npm run build`, start
`npm start`, and set the same environment variables.

## Self-hosting on your own machine

No accounts at all:

```bash
npm run setup
npm run build
npm start
```

Serves on `http://localhost:4000` with a local SQLite file and local uploads. To let other
devices on your network connect, keep `HOST=0.0.0.0`, allow Node through the firewall, and
share `http://<your-lan-ip>:4000`.

To expose it to the internet temporarily, [Cloudflare Tunnel](https://developers.cloudflare.com/pages/how-to/preview-with-cloudflare-tunnel/)
is free:

```bash
cloudflared tunnel --url http://localhost:4000
```

Set `PUBLIC_URL` to the tunnel URL and `COOKIE_SECURE=true` before doing so.
